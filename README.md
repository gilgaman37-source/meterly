# Meterly — Gas & Water Usage Monitoring Application

Meterly — приложение для учёта показаний счётчиков холодной воды, горячей воды и газа. Проект содержит REST API на Java 21 + Spring Boot, PostgreSQL-хранилище, OCR-пайплайн на OpenCV/Tesseract, пользовательский интерфейс, аналитический дашборд и административную панель.

## Что реализовано

- Регистрация и вход по логину/паролю.
- JWT-аутентификация и роли `USER`, `ANALYST`, `ADMIN`.
- Сущность счётчика: серийный номер, тип, регион, описание, активность.
- Отдельный учёт типов `COLD_WATER`, `HOT_WATER`, `GAS`.
- Ручная передача показаний.
- Передача показаний по фото через OCR.
- Сохранение изображения на диск перед обработкой.
- FIFO-очередь OCR-запросов.
- Статусы обработки: `QUEUED`, `PROCESSING`, `COMPLETED`, `FAILED`, `REQUIRES_CONFIRMATION`.
- PostgreSQL + Flyway-миграции.
- Расчёт потребления и платежей.
- Поддержка одиночного тарифа и двухкомпонентного тарифа горячей воды.
- Дашборд аналитика с графиками и точными таблицами значений.
- Админ-панель для пользователей и тарифов.
- Тесты backend и frontend-сборка.

## Роли

### USER

Обычный пользователь системы.

Может:

- создавать и редактировать свои счётчики;
- передавать свои показания вручную;
- загружать фото счётчика;
- смотреть свои OCR-запросы;
- подтверждать спорный OCR-результат;
- смотреть свои платежи.

Не может:

- видеть данные других пользователей;
- открывать аналитику по всей системе;
- менять тарифы;
- менять роли.

### ANALYST

Аналитик работает с обезличенными агрегированными данными.

Может:

- открывать раздел `Аналитика`;
- смотреть суммарные платежи по месяцам;
- смотреть платежи по типам счётчиков;
- смотреть круговую диаграмму долей платежей;
- смотреть средний платёж по месяцам;
- смотреть среднее потребление воды и газа;
- смотреть статистику OCR-запросов;
- использовать фильтры периода и типа счётчика.

Не может:

- управлять пользователями;
- менять тарифы;
- редактировать чужие счётчики и показания.

### ADMIN

Администратор управляет системными настройками.

Может:

- всё, что может аналитик;
- открывать раздел `Администрирование`;
- смотреть список пользователей;
- менять роли пользователей;
- включать и отключать пользователей;
- создавать, редактировать и удалять тарифы.

Защита: текущий администратор не может отключить сам себя или снять с себя роль `ADMIN`.

## Архитектура

```text
React / TypeScript frontend
        |
        | REST + JWT
        v
Spring Boot controllers
        |
        v
Service layer
        |
        +--> PostgreSQL / JPA / Flyway
        |
        +--> Local image storage
        |
        +--> OCR FIFO queue
                 |
                 v
              Worker
                 |
                 v
          OpenCV + Tesseract
```

PostgreSQL является источником истины. In-memory FIFO-очередь используется как диспетчер: при рестарте backend незавершённые OCR-запросы восстанавливаются из таблицы `ocr_requests`.

## Как работает OCR

1. Пользователь загружает фото.
2. Backend проверяет тип файла, размер и возможность декодировать изображение.
3. Файл сохраняется локально в `backend/data/uploads`.
4. В PostgreSQL создаётся запись `ocr_requests`.
5. Запрос получает статус `QUEUED`.
6. ID запроса помещается в FIFO-очередь.
7. Worker берёт запросы по одному и переводит их в `PROCESSING`.
8. OpenCV выполняет предобработку:
   - grayscale;
   - blur;
   - бинаризация Otsu;
   - Canny/контуры;
   - поиск области с цифрами;
   - нормализация crop.
9. Tesseract распознаёт число.
10. Результат проверяется:
   - значение не отрицательное;
   - дата не в далёком будущем;
   - значение не меньше предыдущего, если не отмечен сброс счётчика;
   - уверенность OCR выше порога.
11. Если всё хорошо, создаётся `meter_reading`.
12. Если есть сомнения, запрос получает `REQUIRES_CONFIRMATION`.

## Очередь OCR

Очередь реализована как FIFO-структура:

```text
upload image -> save file -> create OCR request -> enqueue requestId -> worker processes in order
```

Пока запрос стоит в очереди, изображение уже сохранено локально, а состояние запроса хранится в PostgreSQL. Это защищает систему от потери данных при задержке обработки.

Для production можно заменить in-memory очередь на RabbitMQ, Kafka или Redis Streams, а локальное хранилище — на S3-совместимое объектное хранилище.

## Расчёт потребления

Потребление считается по соседним завершённым показаниям одного счётчика:

```text
consumption = current_value - previous_value
```

Если значение меньше предыдущего и пользователь не указал замену/сброс счётчика, показание отклоняется.

Если был сброс или замена счётчика, новая запись становится новой базовой точкой.

## Расчёт платежей

В системе поддержаны два метода тарификации.

### SINGLE_RATE

Используется для холодной воды и газа.

```text
payment = consumption * price_per_unit
```

Пример:

```text
10 м³ * 70 RUB/м³ = 700 RUB
```

### TWO_COMPONENT_HOT_WATER

Используется для горячей воды, где тариф может состоять из двух компонентов:

```text
effective_price = water_component_per_m3 + heat_component_per_gcal * heat_norm_gcal_per_m3
payment = consumption * effective_price
```

Пример:

```text
water_component_per_m3 = 73.79 RUB
heat_component_per_gcal = 3800.68 RUB
heat_norm_gcal_per_m3 = 0.06

effective_price = 73.79 + 3800.68 * 0.06 = 301.8308 RUB/м³
```

Такой способ лучше подходит для горячей воды, потому что во многих муниципалитетах тариф ГВС задаётся через компонент холодной воды/теплоносителя и компонент тепловой энергии.

### Смена тарифа внутри периода

Если между двумя показаниями тариф менялся, backend делит расход пропорционально по дням.

Пример:

```text
Период: 1 января — 30 января
Расход: 60 м³
Тариф 1: 1–15 января
Тариф 2: 16–30 января
```

Система считает дневное потребление и суммирует:

```text
payment = daily_consumption * tariff_for_each_day
```

## Обучение OCR-модели

Основной OCR в backend основан на OpenCV + Tesseract. Для демонстрации и хороших фото этого достаточно,
но для реальных фото качество ограничено, поэтому дополнительно добавлен локальный pipeline обучения
нейросетевой модели на датасете Kaggle.

В текущей версии OCR дополнительно усилен:

- область дисплея ищется не только контурами, но и через Hough Lines;
- Tesseract запускается в нескольких page segmentation modes;
- результат выбирается по лучшему числовому кандидату, а не по первому найденному фрагменту;
- добавлен дополнительный вариант адаптивной бинаризации;
- добавлен golden-набор из 20 синтетических цифровых примеров.

Файл golden-набора:

```text
backend/src/test/resources/ocr/golden-digital-samples.csv
```

Тест:

```text
backend/src/test/java/com/example/metermonitor/ocr/OpenCvTesseractOcrEngineTest.java
```

Он генерирует изображения по CSV и проверяет, что все 20 значений распознаются точно.

Для обучения использован датасет:

```text
YandexToloka Water Meters Dataset на Kaggle
```

Локальное расположение после скачивания:

```text
work/datasets/yandextoloka-water-meters/WaterMeters
```

Добавленные файлы обучения:

- `ml/prepare_yandextoloka.py` — вырезает и выравнивает область показаний по polygon-разметке из `data.csv`;
- `ml/train_crnn.py` и `ml/predict_crnn.py` — экспериментальный CRNN baseline;
- `ml/train_digit_cells.py` и `ml/predict_digit_cells.py` — основной обученный baseline для механических водосчётчиков;
- `backend/src/main/java/com/example/metermonitor/ocr/PythonDigitCellOcrEngine.java` — интеграция обученной модели в Spring OCR pipeline;
- `ml/golden-kaggle-validation-digit-cells.csv` — 20 реальных validation-примеров, которые обученная модель распознаёт точно.
- `examples/ocr-upload-samples` и `examples/ocr-upload-samples.zip` — те же 20 примеров в виде PNG для загрузки через сайт.

Результат локального CPU-обучения digit-cell модели:

- около `87%` точности по отдельным цифрам;
- около `53-54%` точности по полному показанию на validation split;
- 20 точных validation-примеров вынесены в отдельный CSV для демонстрации.
- эти 20 PNG также проверены через реальный endpoint загрузки: `20/20` запросов завершились статусом `COMPLETED`.

Запуск backend с обученной моделью:

```powershell
$env:APP_OCR_ENGINE="digit-cells"
$env:OCR_DIGIT_MODEL_PATH="../work/ocr-training/digit-cells/best_digit_model.pt"
$env:OCR_DIGIT_PREDICT_SCRIPT="../ml/predict_full_meter.py"
mvn spring-boot:run
```

Почему выбран digit-cell подход: механический водосчётчик обычно содержит 8 барабанов, где последние
3 цифры являются дробной частью. Модель классифицирует каждую цифровую ячейку отдельно, затем значение
форматируется как `XXXXX.XXX` без ведущих нулей. Это лучше соответствует устройству счётчика, чем
попытка сразу распознать строку без ведущих нулей.

Что ещё нужно для production-качества:

1. Дообучить модель дольше на GPU.
2. Улучшить выравнивание восьми цифровых ячеек перед классификацией.
3. Добавить отдельный детектор области дисплея для произвольных пользовательских фото.
4. Интегрировать обученную модель в backend рядом с Tesseract как fallback/ensemble.
5. Оставить ручное подтверждение для низкой уверенности.

Файл `kaggle.json` не должен попадать в репозиторий. Его нужно хранить вне проекта или в локальном защищённом каталоге.

## Ограничения

- Backend по умолчанию пока использует Tesseract + предобработку; обученная PyTorch-модель подготовлена
  как локальный baseline и требует отдельной интеграции в Java API.
- Тарифы нужно поддерживать актуальными через админ-панель.
- Для production нужна внешняя очередь: RabbitMQ, Kafka или Redis Streams.
- Для production нужно объектное хранилище вместо локального диска.
- Нужны rate limiting, аудит действий администратора и защита от перебора паролей.
